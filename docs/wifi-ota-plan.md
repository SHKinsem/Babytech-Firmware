# Wi-Fi 固件升级计划

> 本文记录实施前的评估与验收目标。当前代码进展和使用步骤见 [Wi-Fi 固件升级：实现与使用](wifi-ota-implementation.md)。

## 结论与范围

可以实现。首版采用**浏览器连接板卡 Wi-Fi，手动上传对应板卡的 `firmware.bin`**：设备控制板可通过自身热点或已连接的局域网访问；主控板目前只开热点，通过 `Babytech-Debug` 访问。两块板分别升级，不经 UART 互相转发固件，也不依赖云服务。

当前两块板均为 ESP32-S3 N16R8，PlatformIO/Arduino-ESP32 2.0.11。`default_16MB.csv` 的现有编译产物已包含 `otadata`、`app0`、`app1`，每个应用槽为 `0x640000`（6.25 MiB）。2026-09-23 的构建产物：设备板 `1,288,608` 字节、主控板 `736,160` 字节，均远小于单槽容量。网页已嵌入应用镜像，无需另更新 SPIFFS。以上确认的是仓库产物；首次升级前仍需从实板读回分区表，确认其与构建产物一致。

现有固件尚无 OTA 接口。第一次启用 OTA 必须通过 USB/串口烧录带 OTA 功能的版本，之后才能通过 Wi-Fi 升级。上传时只接收该板的**应用镜像 `firmware.bin`**；`bootloader.bin`、`partitions.bin`、`boot_app0.bin` 不能作为网页升级文件。

## 实现设计

1. 为两块板分别加入同一套小型 OTA 模块，接入现有 `WebServer`。提供状态、创建升级会话、上传镜像和查询结果的接口；页面显示板卡型号、当前版本、目标版本、文件大小及上传进度。上传按块写入非运行中的 OTA 槽，绝不把整个镜像读入 RAM。
2. 发布包包含板卡类型、硬件兼容标识、版本、镜像长度和 SHA-256 摘要。设备在开始写入前验证发布信息的签名与目标板卡；写入时累计长度和摘要，核对成功后才结束写入并切换启动槽。设备板与主控板的镜像即使同为 ESP32-S3，也必须互相拒绝。升级接口需要独立的管理凭据；现有共用开发热点密码不能充当升级授权。凭据不得写入日志或网页响应。
3. 设备板在整个上传、校验、重启期间进入维护状态，拒绝新的运动、使能、队列启动及 Wi-Fi 配置变更。只有 UART 执行、队列、CAN 操作均不忙且已跟踪电机全部失能时，才能开始上传。现有 `motionBusy()` 可作为初步门禁，但需补充未跟踪的原始 CAN 命令及物理停机检查。正式升级规程要求先停机并切断电机动力电源；软件状态本身不足以证明所有电机已静止。现有同步 `WebServer` 处理长时间上传时，不能保证同时响应另一个 HTTP 停止请求，所以必须先完成物理安全隔离；若以后要求带电升级，需先将运动监督与停止通道移出上传处理路径并单独验收。
4. 主控板升级前也要求整机处于维护状态。升级期间其 UART 轮询会短暂停止，不能在设备板执行动作时升级主控板。两板应按协议兼容表逐一升级并在每一步确认通信恢复；将来如果协议变更，先做兼容过渡版本。
5. 上传失败、连接断开或断电时放弃未完成镜像，继续启动旧槽。新版本首次启动后先检查基本服务、配置读取和板间通信，再显式确认新固件有效；检查失败触发回退。当前工具链的 ESP32-S3 配置启用了 bootloader rollback，但 Arduino 核心默认会在 `setup()` 前调用弱函数 `verifyOta()` 并立即把新镜像标记为有效。因此实现时必须接管该默认行为，延迟确认，并在实板验证启动失败回退。不能仅凭双分区就宣称具备自动回退。
6. 保留 NVS 中的 Wi-Fi、称重和电机配置。升级接口不得擦除整片 Flash、改写分区表或重写 `otadata` 以外的数据分区。发布包明确固件版本与配置版本；若未来配置格式改变，迁移代码须能处理回退后的旧版本。

## 建议实施顺序

1. 固定发布包格式、板卡 ID 和版本号；在打包工具中生成摘要、签名与清单，并加上两板镜像交叉校验。
2. 先在主控板实现 OTA 核心和热点网页上传，验证分块写入、断线保留旧固件、错误镜像拒绝及新固件启动。
3. 复用 OTA 核心接入设备板，加入维护状态及运动门禁；上传开始前确认电机动力电源已隔离，避免现有同步 HTTP 上传阻塞运动控制轮询。
4. 两板实现首次启动健康检查及延迟确认；分别验证自动回退。更新 `tools/package-device.py` 和交付文档，使发布包及版本记录可追溯。
5. 台架验收：先断开电机动力电源，依次验证两板升级、错板镜像、错误摘要/签名、上传中断、断电、首次启动崩溃、NVS 保留、跨版本 UART 兼容。最后在受控实机环境中检查升级前后停止与失能行为。

## 当前代码接入点

- `main-controller/src/main.cpp`：现有热点、`WebServer` 和主控板 UART 轮询。
- `device-controller/src/main.cpp`：设备板 HTTP 路由、运动/队列/UART 轮询及 `motionBusy()`。
- `device-controller/src/WiFiSetup.cpp`：设备板 AP+STA、配网忙碌状态。
- 两个 `platformio.ini`：均选用 `default_16MB.csv`。
- `tools/package-device.py`、`tools/flash-device.py`：现有串口发布包和首次安装流程；OTA 发布包需单独定义，不能直接上传四镜像包。
