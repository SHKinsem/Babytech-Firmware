# Babytech 运动控制 —— AP + 单电机调试页（MVP）

> 本文保留基础 API 与控制器行为说明。最新工作台、Wi-Fi 集成、扩展命令范围和交付流程见 [工作台交付说明](motion-workbench-release.md)；下文旧页面布局说明已被新版替代。

面向 ESP32-S3 运动板卡的单电机台架工具。板卡开启 WiFi 软 AP，提供一个自包含的
调试页面，并通过 `motion::MotorControl` 经 CAN 把 HTTP 命令转发给电机驱动。

接口定位（本迭代）：

* 本文基础受监督入口是**单电机台架 API**；独立的 [编排队列](motor-queue.md) 按顺序直发，非等待动作可以重叠，但可靠双电机执行仍有待排查的实机问题，不能将单电机门禁概括为所有入口的行为。
* **尚无同步 / 联动 / 插补语义**，也没有相关接口，页面上也没有同步标签页。
* 页面只原样呈现 `/api/status` 上报的数据，**不做任何推断**：不推断命令已被驱动
  确认，也不推断已启动、已完成或已物理停止。
* 机械运行时在脑板链路上仍为 `not_configured`：HX711 已由下板独立采样并开放 HTTP
  API，但称重数据暂未加入脑板 UART 状态载荷。
* 本文只描述接口契约与页面行为，不含构建、烧录或测试结论。

本切片涉及的文件：

| 文件 | 作用 |
| --- | --- |
| `motion/include/board_config.h` | UART、CAN 与软 AP 常量 |
| `motion/src/main.cpp` | AP + HTTP 服务 + 脑板链路状态桥 |
| `motion/data/index.html` | 内嵌调试页（内联 CSS/JS，无外部依赖） |
| `docs/motion-debug.md` | 本文档 |

用户报告两条不同电机的非等待 `move` 仅一台运动，当前根因未确认。以下是待执行的复现步骤，不是已完成的实机验证：

1. 保存完整程序、循环次数、固件版本、两台地址及参数，分别单独运行对应移动，确认每台的基线行为。
2. 在可观察的台架条件下连续执行两条，交换顺序再对照；记录是固定某台不动，还是固定第二条不执行。
3. 保存两台完整 CD 发送分包、驱动应答和位置反馈；区分未提交发送、驱动拒绝、接受未确认和接受后未观察到位移。TX 日志不等于驱动接收证明。
4. 加短间隔仅作为对照试验，不能直接当作最终修复；检查后续同轴命令、停止/失能及循环是否打断动作。

现有常规查询与 await 查询分别调度，可能叠加；500 kbit/s 是 CAN 配置，不代表驱动可处理的请求上限。后续将统一查询预算、去重和按阶段申请反馈，见 [修复与低带宽同步计划](motor-sync-plan.md)。吞吐测试应独立进行，不与实际拧盖动作同时进行。

## 2. 引脚与接线

| 信号 | GPIO | 说明 |
| --- | --- | --- |
| 脑板链路 TX | 43 | UART1 接脑板，115200 8N1 |
| 脑板链路 RX | 44 | UART1 接脑板 |
| CAN TX | 4 | 接外部收发器 TXD/CTX 输入 |
| CAN RX | 5 | 接外部收发器 RXD/CRX 输出 |
| CAN 波特率 | 500 kbit/s | 沿用已验证的台架配置 |
| HX711 DOUT | 1 | 3.3 V HX711 数据输出 |
| HX711 SCK | 2 | 3.3 V HX711 时钟，空闲保持 LOW |

HX711 引脚集中在 `motion/include/board_config.h`。新板型可以修改默认值，也可以在
构建参数中指定 `BABYTECH_SCALE_DOUT_PIN` 与 `BABYTECH_SCALE_SCK_PIN`；编译期冲突
检查会阻止它们与 CAN 或脑板 UART 引脚重叠。

**ESP32-S3 片上没有 CAN 收发器。** 这些引脚只是 CAN 控制器，必须外接 3.3 V 逻辑
收发器（SN65HVD230 / TJA1051T/3 一类）。仅 5 V 的收发器（如经典 TJA1050）需要在
TXD 上做电平处理，并且无法安全地把 RX 电平送进 3.3 V 引脚。

给驱动器上电之前：

1. **共地** —— ESP32-S3、收发器与电机驱动必须共用同一个地参考。这是“电机不
   在线”最常见的原因。
2. **终端电阻** —— 总线**两端**（板卡端与最远驱动端）各接 120 Ω，跨接
   CANH/CANL。总线断电时测 CANH/CANL 应约为 60 Ω；测到 120 Ω 说明只有一端有
   终端电阻，阻值很高说明两端都没有。
3. **收发器供电** —— VCC 接 3.3 V，地接公共地；若模块本身没有去耦电容就补一个。
4. **避免长分支** —— CANH/CANL 走线要短、要绞合，不要加长支线；长支线会让页面
   上报的 TX 错误计数上升，先偶发，后持续。
5. **用页面验证，不要靠假设** —— 必须等页面上的 `busState` 离开错误状态、目标 ID
   显示 `online` 之后，才谈得上使能。空闲时 `txErrors` 还在上涨，说明是接线或
   终端电阻问题。

## 3. HTTP 接口

所有响应都是 JSON，并带 `Cache-Control: no-store`。`ok` 是权威的成功标志：只有固件
结果码小于 300 时为 `true`。HTTP 状态码就是固件结果码。

`POST` 请求体为 `application/x-www-form-urlencoded`（浏览器表单编码）。

### `GET /`

返回内嵌调试页。页面被编译进固件镜像（单个 blob，无文件系统，无 CDN）。

### `GET /api/status?id=<1..255>`

把该 ID 登记为被监视对象，并原样返回完整状态对象。

```bash
curl -s "http://192.168.4.1/api/status?id=1"
```

响应结构（契约来自 `MotorControl::statusJson`）：

```json
{
  "id": 1,
  "canReady": true,
  "busState": "active",
  "txErrors": 0,
  "activeId": 0,
  "state": "idle",
  "enabled": true,
  "online": true,
  "positionDeg": 12.5,
  "speedRpm": 0.0,
  "currentMa": 0,
  "ageMs": 41,
  "lastAck": "position"
}
```

字段含义：

* `online` —— 收到了新鲜的位置**和**速度数据；这是唯一可信的“驱动在通信”标志。
  数值未知时 `positionDeg`/`speedRpm`/`currentMa` 为 `null`，页面显示 `—`，
  并且不添加图表采样点。
* `canReady` —— CAN 已就绪、可以收发；它是页面放行使能/失能/运动按钮的必要条件。
* `enabled` —— 后端上报的使能状态，页面只原样显示，不据此判定任何命令成功。
* `activeId` —— `0` 表示没有正在运动的节点；页面只把它当作数据展示，不据此判定
  命令被确认或已完成。
* `ageMs` —— 最新位置/速度采样的年龄。
* `lastAck` —— 最近被确认帧的标识，页面原样显示，不做任何推断。
* `state`、`busState` —— 英文标识符，按原文显示。
* 该 JSON **没有** `uptime` 字段。

错误：`id` 缺失 / 为 `0` / 为 `256` / 非数字 → `400`，
`{"ok":false,"message":"id must be an integer 1..255"}`。

### HX711 称重 API

称重功能完全运行在 motion 下板。内嵌网页的「称重传感器」页使用这些接口显示合成
重量、最近 60 秒漂移、诊断信息，并执行去皮和砝码标定。

`GET /api/scale` 返回最新称重快照：

```bash
curl -s http://192.168.4.1/api/scale
```

响应包含当前 `doutPin` / `sckPin`、`status`、`available`、`calibrated`、`stable`、`rawCounts`、`netCounts`、
`rawWeightG`、`weightG`、`sampleAgeMs`、去皮状态和当前标定参数。没有有效值的数值字段
为 `null`，页面不得据此制造占位读数。

网页「称重传感器」页右侧的「诊断信息」中可点「配置 IO」修改引脚。对应接口为：

```bash
curl -s -X POST -d "doutPin=6&sckPin=7" \
  http://192.168.4.1/api/scale/config
```

允许使用 GPIO 1、2、6..18、21、38..42、47、48，且 DOUT 与 SCK 不能相同。GPIO45
仅在固件确认 `VDD_SPI_FORCE=1` 且 `VDD_SPI_TIEH=1`、即 Flash 供电已由 eFuse 固定为
3.3 V 时开放。CAN、板间 UART、原生 USB、其余启动绑带以及外部 Flash/PSRAM 引脚均被保留。配置保存到 `scale-io`
NVS 命名空间并立即重新初始化 HX711，重启后继续使用；默认值仍为 DOUT GPIO1、SCK GPIO2。

空载且所有电机静止时发起去皮：

```bash
curl -s -X POST http://192.168.4.1/api/scale/tare
```

接口返回 `202 tare_started`，下板异步采集 16 个样本。轮询 `/api/scale`，等待
`tareInProgress=false` 且 `tareCompleted=true` 后放置已知砝码，再标定：

```bash
curl -s -X POST -d "knownWeightG=500" \
  http://192.168.4.1/api/scale/calibrate
```

`knownWeightG` 范围为 1..5000 g。去皮和标定均在机构运动期间返回 `409`；标定要求
本次启动已完成去皮且读数新鲜。成功的 `tareRaw` 与 `countsPerGram` 保存到下板 NVS 的
独立 `scale-cfg` 命名空间，重启后继续使用。实际出粉闭环尚未接入这组读数。

### `POST /api/enable`

| 字段 | 值 |
| --- | --- |
| `id` | 整数 1..255 |
| `enabled` | 只能是 `0` 或 `1` |

```bash
curl -s -X POST -d "id=1&enabled=1" http://192.168.4.1/api/enable
# {"ok":true,"message":"..."}
curl -s -X POST -d "id=1&enabled=0" http://192.168.4.1/api/enable
```

### `POST /api/move`

从当前位置做相对运动。**不会自动使能** —— 驱动未使能或有其他运动进行中时，请求
会被拒绝。

| 字段 | 类型 | 范围 |
| --- | --- | --- |
| `id` | 整数 | 1..255 |
| `angle` | 数字，非零 | -3600..3600 deg（带符号，相对） |
| `speed` | 数字 | 0.1..120 rpm |
| `accel` | 整数 | 1..240 rpm/s |
| `decel` | 整数 | 1..240 rpm/s |
| `current` | 整数 | 100..5000 mA |

```bash
curl -s -X POST \
  -d "id=1&angle=10&speed=5&accel=10&decel=10&current=800" \
  http://192.168.4.1/api/move
```

校验很严格：只接受完整的数字字面量。`12abc`、`1e3`、`nan`、`inf`、` 12`、整数字段
写 `12.5`、空字段或缺失字段，都会在**任何收窄转换之前**以 `400` 拒绝。任何地方都
没有使用 `String::toInt()` 那种静默接受垃圾的写法。

### `POST /api/stop` 与 `POST /api/stop-all`

```bash
curl -s -X POST -d "id=1" http://192.168.4.1/api/stop
curl -s -X POST http://192.168.4.1/api/stop-all
```

### 如何理解返回码

* **`202` 只表示“在本板排队”。** 它绝不表示驱动已确认、已启动、已完成或已物理
  停止。页面也照此说明，不会把排队当成成功；页面只记录后端状态的后续变化，并把
  `lastAck` 原样显示出来。
* `4xx` 来自处理函数 = 请求被拒绝（校验失败或固件拒绝）；`message` 是可读原因。
* `404` = 未知路径。`405` = 已知路径但方法错误。
* 页面不会自动重试 `POST`。一次点击，一个请求。

## 4. 调试页行为

* 全部可见文案为简体中文；保留 API 路径、动作标识、JS 元素 ID、`state`/`busState`
  等后端标识符，以及 RPM / deg / mA / ms 单位与 CAN ID。
* 字体为 Segoe UI / Microsoft YaHei UI，正文与标题使用常规字重（400/500），不用
  等宽字体显示大数值；数字使用表格数字（tabular-nums）。
* 顶部有 AP 提示与连接指示灯，由真实状态驱动。页面没有任何示例/伪造数据：未知值
  一律显示 `—`。
* **目标 CAN ID** 可编辑（1..255）。输入框内容一变成合法 ID 就立即切换控制目标，
  因此在切换生效前，命令绝不会发往旧 ID；输入框里是非法文本时，所有目标操作一律
  禁用，失焦时把非法文本还原为当前目标。切换目标只切换控制对象，绝不写驱动器
  地址。每个 ID 的参数草稿保存在浏览器标签页内存里（刷新即丢失，仅内存）。切换
  时立即清空实时值与图表历史，并作废上一个 ID 的在途响应，旧遥测不会出现在新
  ID 下。
* **一行紧凑参数**：角度（带符号，相对）、速度、加速度、减速度、电流，外加
  10°/90°/360° 快捷按钮与反向按钮。
* **显式按钮**：使能、失能、运动、停止**目标**，以及全部停止。
  * 使能与运动需要状态新鲜、`canReady`、`online`、`enabled`，并且（运动时）
    `activeId` 为 `0`、参数通过校验。
  * 失能是纠正性指令：只要状态新鲜且 `canReady` 就可发送，不要求所选节点在线，
    也不要求当前 `enabled` 为真。
  * 一次 HTTP 请求进行中会短暂禁用目标按钮；**全部停止**只受自身在途状态限制，
    始终可独立调用。
  * 使能永远是单独的一次点击，页面不会代办。
* **反馈行**：位置、速度、电流、驱动状态、CAN 总线、已使能、活动 ID、采样年龄、
  CAN 发送错误、最近驱动确认 `lastAck`。页面只原样显示后端值：不把 `activeId`
  变成目标值当成命令被确认，也不把 `enabled` 变成某个值当成完成或停止已完成。
* 页面只**记录后端状态变化**（`state`、`activeId`、`enabled` 变化时各写一条日志），
  `lastAck` 只按原文显示，绝不推断“已确认 / 已完成 / 已停止”。
* **图表**：所选 ID 最近 ≤200 个真实位置采样，按实际带符号绝对位置（deg）绘制。
  断连或 `null` 读数会留下明显缺口——不插值，不伪造轨迹。
* **事件日志**：可折叠、带时间戳、最多 100 条、可清空。它记录页面/HTTP 事件，
  不是原始 CAN 报文。
* 每 300 ms 轮询一次状态，超时 1500 ms（`AbortController`），请求不重叠。与板卡
  失联时清空实时值并禁用运动控制；图表保留历史并留出缺口。
* 布局：14 px 中文字体栈，390 px 宽度起可用。无网络字体、无外部脚本、无 CDN。

## 5. 脑板链路（协议不变，只是载荷来源换了）

板卡仍使用既有的 `BoardProtocol` 组帧，在 UART1 上以 115200 通信：带**空载荷**的
`GetStatus` 帧会收到一个回显请求序号的 `Status` 帧。六个载荷字节为：

| 字节 | 含义 |
| --- | --- |
| 0..3 | 运行时间（毫秒，小端） |
| 4 | 运动状态，`0` = `not_configured`（机械运行时尚未接入） |
| 5 | 标志位，bit0 = `motorsAvailable`（`anyMotorOnline()`），bit1 = `sensorsAvailable`（恒为 0） |

脑板侧 `Babytech` 代码与 `BoardProtocol` 在本切片中**不做修改**。载荷非空的查询、
以及其他类型的帧都会被忽略。每轮循环最多读取 128 字节 UART，以免链路噪声饿死
CAN 轮询或 HTTP 处理。

要注意：这个运行时间只存在于脑板链路帧里，`/api/status` 的 JSON 没有 `uptime` 字段。

本文不给出构建或烧录命令，也不对构建、烧录或测试结果作任何声明。板卡启动时只打印
AP、CAN 与 HTTP 监听信息，并且**不发送任何使能或运动命令**（驱动器可能此前就已是
使能状态）。

## 7. 台架检查清单（计划，尚未执行）

开始时机械部分应**空载且可自由转动**。

1. 只给板卡上电（总线无活动）。串口打印 AP 信息。加入 `Babytech-Motion`，打开
   `http://192.168.4.1/`。
2. 页面加载，连接指示灯稳定，`busState`/`txErrors` 有更新。驱动断电时：`online`
   应为 false，数值为 `—`，运动按钮禁用，全部停止仍可点击——后者是有意设计，不是
   缺陷。
3. 给驱动器上电。目标 ID 应在几次轮询内变为 `online`，`txErrors` 保持平稳。错误
   计数上升或总线状态长期为错误，说明接线/终端电阻有问题——回到第 2 节。
4. **使能**，确认反馈行“已使能”显示“是”（这是后端上报的值，不是点击本身），
   此时运动按钮才解锁。
5. 首次运动采用保守参数：`angle 10`、`speed 5`、`accel 10`、`decel 10`，`current`
   取对硬件合适且偏低的值。只点击一次运动。提示先显示“已受理……”，之后当状态里
   `activeId` 变化时，事件日志会出现“后端 activeId 变为 …”。
6. 确认图表按指令方向显示真实位置（deg）变化，且驱动回到空闲、无故障状态。
7. 运动中以同样的小参数**停止**：`activeId` 应回到 `0`；日志只记录后端状态变化，
   不声称“停止已完成”。
8. 空闲时**失能**，确认“已使能”显示“否”，并确认运动会被拒绝（由固件拒绝，而不
   只是页面禁用按钮）。
9. 在选中 ID 运动时点**全部停止**：请求仍应被受理（它允许在其他请求进行中发出），
   且运动结束。
10. 运动中刷新页面：应回到 `—`，然后出现真实值，并且加载时绝不发出任何命令。
11. 页面打开时拔掉驱动总线：数值清空为 `—`，运动按钮禁用，图表出现缺口，日志记录
    状态丢失。
12. 以上全部通过后，再尝试更大的运动（90°，然后 360°）。

## 8. 来源说明与后续工作

* UART 组帧、CRC、解析超时以及 `GetStatus`/`Status` 语义来自既有的
  `BoardProtocol` 库和上一切片已交付的脑板侧代码；本文件只改变了回复的载荷来源
  （电机可用性标志）。
* CAN 收发器引脚与波特率沿用此前已验证的单电机台架配置。

本迭代有意不做的事：

* 多轴同步 / 协调运动（**尚无同步功能**，也没有同步标签页），
* 命令批处理或轨迹预载，
* 参数持久化（草稿只存在于浏览器内存；不写入 flash，也不写入驱动器），
* 传感器遥测（链路标志 bit1 保持为 0），
* 强制门户、OTA 升级、AP 鉴权。


## 已知限制与后续档案

- CAN 发送使用迁入的同步驱动，每帧可能等待 50 ms；HTTP 服务同样为同步服务。此版本不是硬实时控制器，网页停止不是硬件急停。
- CAN bus-off 后当前版本需要重启板卡恢复总线，不会自动续跑旧动作。
- `enabled` 是本次应用请求获得 ACK 的记录，不是独立读取的驱动使能位；电机掉电、外部控制等情况要重新确认。
- 驱动 ACK 没有序列号；不并行发送运动，重复或极迟 ACK 的强关联留待后续。停止后的待处理使能会被取消。
- 未收到停止后的新静止反馈时保持 stop_requested；离线节点可能使新使能被拒绝，需要恢复该节点或重启调试板，不能据此声称电机已经停下。
- 当前 ID 输入只选择控制目标，不修改驱动器地址。多电机同步、驱动地址修改、参数持久化、传感器和机构保护联锁暂未实现。
- 本轮软件验证不代替电机型号/固件版本的实机验收，尤其是加速度单位、相对当前位置模式 2、反馈与 ACK 行为。

自动验证：运行 python tools/test_motion.py（需要 g++）测试协议和真实状态机；node tests/motion-web.spec.cjs 测试网页模拟接口（需要 Playwright 和 Edge，可用 PLAYWRIGHT_MODULE 指定模块路径），截图写入 out/web-tests。status JSON 的 fault 字段直接显示锁存的故障原因。


## Wi-Fi 配置（AP + STA）

展开页面顶部的「Wi-Fi 设置」，扫描附近的 2.4 GHz 网络，或手动填写 SSID（包括隐藏网络），输入密码后点「保存并连接」。留空密码表示开放网络；当前不支持企业认证。配置保存到板卡 NVS，重启后自动尝试连接；失败后每 30 秒重试，电机运动时延后重试。「忘记网络」只删除本模块的网络配置并断开路由器。

连接成功后页面显示局域网 IP；电脑连到同一路由器后可通过该地址访问调试页。原热点 `Babytech-Motion` / `babytech-demo` 保持开启，重连热点后可访问 `http://192.168.4.1/`。

ESP32-S3 只有一个 2.4 GHz 无线电：AP+STA 模式支持扫描，但扫描或连接路由器可能造成热点连接短暂延迟/中断，AP 信道会跟随 STA。因此“保持开启”不保证网页连接不中断。扫描与连接互斥；运动期间拒绝扫描/改网，扫描或连接期间拒绝新运动（HTTP 409），停止接口仍接受请求，但不保证无线链路当时可达。热点不提供互联网转发。

接口：GET `/api/wifi` 读取连接状态；POST `/api/wifi/connect`（ssid/password 表单）保存并尝试连接；POST `/api/wifi/forget` 忘记配置；POST `/api/wifi/scan` 启动异步扫描，GET 同路径读取结果。202 表示受理，是否连接成功以状态接口为准。密码不会通过状态 API 返回，网页也不会写入浏览器存储。

本轮验证：WSL motion 编译通过；原有协议和电机状态机测试通过；Wi-Fi 网页模拟接口测试用于验证状态、表单、错误处理和布局。真实无线扫描、密码保存后重启、错误密码及 AP/STA 切信道仍需板上验收。

官方支持依据：[ESP32-S3 Wi-Fi Scan / ESP-IDF 4.4.2](https://docs.espressif.com/projects/esp-idf/en/v4.4.2/esp32s3/api-guides/wifi.html#esp32-s3-wi-fi-scan)。
